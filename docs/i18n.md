# Languages (English, Tamil, Kannada)

| Concern                                                       | Where                                                                                     |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Interface text                                                | `src/messages/{en,ta,kn}.json` (next-intl, ICU message format)                            |
| Languages and routing                                         | `src/i18n/routing.ts` (every URL starts with `/en`, `/ta` or `/kn`)                       |
| Store content (products, categories, banners, home page, SEO) | Per-language fields in the admin                                                          |
| Validation errors                                             | Keys in the `Errors` namespace; Zod's own messages go through `src/lib/validators/zod.ts` |
| Checks                                                        | `pnpm i18n:check` (also in CI and the pre-commit hook) and `tests/unit/i18n.test.ts`      |
| Translations to review                                        | [i18n-review.md](i18n-review.md)                                                          |

## Rules

- **No hard-coded text in components.** Use `useTranslations` / `getTranslations`, and add the key
  to all three files. `pnpm i18n:check` fails on:
  - JSX text
  - `aria-label`, `placeholder`, `title`, `alt` and `label` values
  - toast messages

  Mark real exceptions, such as an example path, with an `// i18n-ignore` comment on the line
  above.

- **Same keys and placeholders everywhere.** The check fails if a key is missing, extra or empty,
  or if a translation's `{placeholders}` differ from English. A dropped `{total}` would silently
  hide the price.
- **Validation messages are keys, never sentences.** Schemas pass keys (`"required"`,
  `"phoneInvalid"`). Zod's built-in errors are mapped to keys globally (`required`, `tooLong`,
  `invalidOption`, …). The browser translates them with `useErrorText`, so errors appear in the
  visitor's language. A unit test runs every schema with bad input and fails on any message that
  isn't a key.
- **Import `z` from `@/lib/validators/zod`** (or `./zod` inside `validators/`) so that global map
  is always loaded.

## Numbers, money and dates

- Prices: `formatINR(paise, locale)` gives Indian grouping (₹1,00,000) in every language.
  Digits stay Latin (0–9), as on most Indian shopping sites, so prices are easy to compare.
- Dates and times: `formatDateTime` and `formatTime`, in Indian time (Asia/Kolkata), with month
  names in the page language.
- Counts: use ICU plurals in messages, e.g. `{count, plural, =1 {# item} other {# items}}`.
- Invoices and packing slips are English-only (see [orders.md](orders.md)).

## Fonts

Noto Sans, Noto Sans Tamil and Noto Sans Kannada are loaded with `next/font`. The Tamil and
Kannada files download only on pages that contain those scripts. Pages in Tamil and Kannada use a
taller line height (1.7) for the tall glyphs and stacked vowel signs.

## Store content in several languages

Product, category, banner, home-section, coupon and SEO text is entered per language in the
admin (tabs on each field). **English is required** and is the fallback: a field left empty in
Tamil or Kannada shows the English text, so a page is never blank. The store name and brand names
are single-language (proper names).

## The visitor's language

- The language switcher changes the URL prefix. It stores the choice in the `NEXT_LOCALE` cookie
  for **one year**, so visiting `/` later opens the store in that language.
- For a signed-in customer, switching also saves it as their **preferred language**, which you can
  also change under My account. It updates the language of their push notifications too.
- Emails, SMS, WhatsApp and push notifications about an order use the customer's **current
  preferred language**, falling back to the language they ordered in.

## Adding or changing text

1. Add the key to `en.json`, then the same key to `ta.json` and `kn.json`. Keep placeholders and
   plural structure identical.
2. Run `pnpm i18n:check` (it also runs when you commit a message file).
3. New customer-facing wording? Add it to [i18n-review.md](i18n-review.md) for a native speaker
   to check.

## Adding a language

Add the code to `locales` in `src/i18n/routing.ts` and to `SW_LOCALES` in `src/sw/routes.ts`.
Copy `en.json` to `<code>.json` and translate it. Add the language's Noto font in
`src/app/[locale]/layout.tsx`. The i18n check then enforces complete, matching keys.
